# Codex automation definitions

Tracked copies of VPK's scheduled Codex jobs (decision D12 in `.agents/docs/hardening-record.md`). The installed jobs live outside the repo at `~/.codex/automations/<id>/automation.toml`; Codex reads only those.

Each file here holds the portable fields: `id`, `kind`, `name`, `prompt`, `status`, `rrule`, `model`, `reasoning_effort` and `execution_environment`. To install one, copy it to `~/.codex/automations/<id>/automation.toml` and append the machine fields `target`, `cwds`, `created_at` and `updated_at` (copy them from an existing job). The repo is public: never put a token or credential in a definition.

- A job that opens pull requests starts its prompt with "Invoke `$vpk-scheduled-automation`" and is listed in `EXPECTED_PRODUCER_AUTOMATION_IDS` in `scripts/verify-saved-producer-automations.mjs`; `node scripts/verify-saved-producer-automations.mjs` checks the installed copies.
- `automation-merge` is the one job that merges (decision D11). It is not a producer: its prompt only runs `scripts/automation-merge.mjs` and reports the JSON, and that script owns every decision. Auto-merge covers only edits to existing READMEs outside `public/` and `app/`, a shrink-only `eslint-suppressions.json`, and the regenerated `.agents/knowledge/repo-map.json` and `.agents/skills/INDEX.md` beside one of those; tests and all other code always need a human (policy data at the top of `scripts/automation-merge-eligibility.mjs`). The script merges an open PR labelled `automation` and `automerge:allowed` only when eligibility passes pinned to the head SHA, Codex approved that SHA or gave a +1 after it reached the PR (dated by a check suite attached to the PR and the latest force-push), the merge commit title is `Merge #<n> (<sha7>)` with no PR text, the `vpk-git-ship` review gate is clear, and eligibility and the Codex signal pass again just before `merge-remote.js` merges that SHA. Producers choose `automerge:allowed` or `risk:needs-human` with the eligibility script's `--policy` mode (`$vpk-scheduled-automation`, step 6). It runs locally with the owner's `gh` auth on purpose: a merge made with an Actions `GITHUB_TOKEN` does not trigger push workflows, so main CI and the Perf budget job would not run.
- Use the latest model of each family (for example `gpt-6.2-sol`, `gpt-6-luna`).
- New drafts are installed with `status = "PAUSED"` until the owner activates them; keep the tracked `status` equal to the installed one. All 20 jobs here are `ACTIVE` as of 20 Nov 2026.
- `standup-summary` is a heartbeat job: its installed copy also has `target_thread_id`, a machine-specific field that is not tracked.
